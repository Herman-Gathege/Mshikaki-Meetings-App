# 17 - UX, Visual Language and Rehearsal

The reference for how Mshikaki should look, behave and sound. If a change
contradicts this document, one of them is wrong. See
[15-phase-6.md](15-phase-6.md) for the phase definition and
[16-ux-audit.md](16-ux-audit.md) for the reasoning behind the biggest changes.

## The one rule

**If a user needs to understand the domain model to know which button to press,
the UX has failed.** Nobody should have to learn the words session, idea,
decision, task, project, activity or XP before using Mshikaki.

Every screen answers three questions: what am I doing, what just happened, what
do I do next.

## Plain language

| Instead of | Write |
|---|---|
| Assign task owner | Who's doing this? |
| Create decision | What did we decide? |
| Launch game session | Let's play |
| Complete session | That's a wrap |
| No records found | Nothing here yet |
| 422 Unprocessable Entity | Hmm, that didn't save. Check the highlighted fields. |

Keep technical detail in the logs and out of the interface. Errors say what
happened and what to try, never a status code.

## Voice

80% clear, 15% personality, 5% surprise. Confirmations are short and warm
("💡 Idea added!", "🎯 Got it. That's yours.", "🎉 That's a wrap!") and dismiss
themselves. Never let personality slow somebody down, and never use it in the
record: the summary and the audit trail stay factual.

## Visual language

- One palette, defined once in `frontend/src/styles/index.css`: paper and ink for
  the record, ember for primary actions, nile for progress and success.
- One type scale, one radius family, one spacing rhythm. Primitives live in
  `components/ui/kit.tsx` and are edited there rather than wrapped again.
- Flat compositions. Cards group related facts; they are not a dashboard grid.
- The skewer metaphor is used for traceability only: the line from a session to
  an idea to a decision to a task. It is never used to rename statuses.
- Playful screens (games, Run Mode, bragging rights) may be loud. The record
  screens stay sober.
- No state is communicated by colour alone. Status badges carry a word and a
  mark.

## Run Mode

Screen-first: it is read from three metres by a room.

- One action per screen, large type, high contrast.
- The journey is named in the facilitator's words: Let's play, What are we
  thinking, What did we decide, Who's got this, That's a wrap.
- Keyboard shortcuts remain available for a host on a laptop.
- It degrades to a usable phone layout, because the facilitator may be on a
  phone.

## The game question lifecycle

Host-paced, never per-phone. The sequence, and what the room sees:

1. **Question** with the pack name and "Question 3 of 10".
2. **Options** as full-width cards, A to D, each entirely clickable.
3. **Timer** counting down beside the question, independent of the network.
4. **Answer** selected once. The selection locks; a second tap cannot submit.
5. **Reveal** after the host confirms: correct or not, the right answer, and the
   explanation when the content carries one.
6. **Score** by tapping the players who got it right; corrections ask for a
   reason and are recorded.
7. **Next question**, or **See results** on the last one.
8. **Results**: winner, standings, session XP so far, and
   **Continue the meeting**, which returns to Run Mode rather than a dashboard.

Nothing is displayed that the system does not store. No invented timings, scores
or rankings.

## The minutes

Generated from the frozen summary at close, never regenerated silently. Nine
sections: meeting details, agenda, opening and play, ideas raised, decisions
made, action items, blockers, closing summary, record information. Downloadable
as a printable document, with the plain-text export kept because it is what
people paste into WhatsApp.

## Empty, loading and error states

- Empty states say what the screen is for and what to do next, with a little
  warmth. "💡 The skewer is empty. Throw the first idea on it."
- Loading states name what is loading ("Getting the game ready…"), so a slow
  connection never looks like a broken screen.
- Errors are human, and never lose what the person typed.

## The rehearsal checklist

The final test is a person, not a test suite. Give Mshikaki to somebody who has
never seen it, say "run a meeting", and help only when they are completely
stuck. Record every hesitation as a defect.

- [ ] They find the meeting and understand what it is for.
- [ ] They start it without being told where the button is.
- [ ] They run a game, and know what to do after the last question.
- [ ] They capture an idea on a phone while talking.
- [ ] They record a decision and assign a task with one owner.
- [ ] They close the meeting and find the minutes without help.
- [ ] They can trace a task back to the meeting that created it.
- [ ] Nobody asks what a status word means.

Run it on a real phone, on the projector, and on a bad connection.
